# Architecture

This document describes the contracts that work package A2 put in place, so that the stage B packages of [V1_PLAN.md](V1_PLAN.md#10-work-packages) can be built in parallel. Read it with [DEVELOPMENT.md](DEVELOPMENT.md) (workspace conventions).

If you are implementing a stage B package, go straight to the [contract table](#contract-table), then read [Conventions](#conventions) and [Things that will trip you up](#things-that-will-trip-you-up).

## Packages and dependencies

Read `A ← B` as "B depends on A":

```
plugin-api ← core ← gaze, prediction, speech, storage, layouts, inference, host
gaze ← gaze-web
host, layouts ← plugin-host
gaze, gaze-web, layouts, prediction ← ui
plugin-api ← plugins/quickfire
core, prediction ← plugins/prediction-ngram
packages and first-party plugins ← apps/web (later apps/desktop, apps/mobile)
```

Every package depends on `plugin-api` and `core`. The extra edges are:

| Package       | Depends on (besides `plugin-api`, `core`)   | DOM allowed |
| ------------- | ------------------------------------------- | ----------- |
| `plugin-api`  | nothing                                     | no          |
| `core`        | `plugin-api` only                           | no          |
| `gaze`        | –                                           | no          |
| `prediction`  | –                                           | no          |
| `speech`      | –                                           | no          |
| `storage`     | –                                           | no          |
| `layouts`     | –                                           | no          |
| `inference`   | –                                           | no          |
| `host`        | –                                           | yes         |
| `gaze-web`    | `gaze`                                      | yes         |
| `plugin-host` | `host`, `layouts`                           | yes         |
| `ui`          | `gaze`, `gaze-web`, `layouts`, `prediction` | yes (React) |

First-party plugins live in `plugins/` as their own packages (`@forsee/plugin-<name>`) and use the public `ForseeApi`; `quickfire` needs only `plugin-api`, `prediction-ngram` also uses `core` and the `prediction` engine directly (first-party plugins may). `apps/web` is the shell: its application runtime (`apps/web/src/runtime`) composes every package and the first-party plugins, and its React entry (`apps/web/src`) mounts the `ui` components on that runtime.

`packages/integration-tests` is a private, test-only package that depends on the other workspace packages to test them together (real kernel, speech engine, prediction engine, layouts and plugin host). Nothing depends on it, and it holds no production code.

There are no cycles and `plugin-api` is the leaf. **Engine packages never depend on `host`**: the platform services they need (`Clock`, `IdSource`, `ProfileFileSystem`) are defined in `core` and injected. Shells (`apps/*`) compose everything.

If your package needs another workspace package, add it to `dependencies` (`"workspace:*"`) **and** to `references` in your `tsconfig.json`, keeping the graph acyclic. Ask before adding an edge not in the table above.

## Conventions

These are stated once in [`packages/plugin-api/src/common.ts`](../packages/plugin-api/src/common.ts) and apply to every type.

**Coordinates.** CSS pixels in the app viewport (the top-level document), origin top-left, x right, y down. `Rect` is `{ x, y, width, height }`; a point is inside when `x <= p.x < x + width` (half-open). Custom-UI panels report rectangles relative to their own frame (`PanelTarget`); the plugin host translates them. Gaze samples may lie outside the viewport.

**Time.** Two clocks, both in milliseconds, both injected through `Clock` (`packages/core/src/platform.ts`):

- **Monotonic** (`clock.now()`, like `performance.now()`): every field named `t` or `*T` (`GazeSample.t`, `Fixation.startT`, `SpeechEvent.t`). Used for dwell, fixations, latency. Only comparable with values from the same host clock; never compare with a sandboxed plugin's own `performance.now()`.
- **Wall** (`clock.wallNow()`, epoch ms): every field named `*At` (`createdAt`, `updatedAt`, `expiresAt`, `savedAt`, `decidedAt`). Used for anything persisted or crossing realms.

Durations are milliseconds and named `*Ms`.

**No ambient platform access in engine code.** No `Date.now`, `performance.now`, `setTimeout`, `Math.random` for ids, or `crypto`. Take a `Clock` and an `IdSource`. Tests use `FakeClock` and `SequentialIdSource` from `@forsee/core`. Real implementations exist only in `packages/host` and the shells.

**Data crossing the plugin boundary** is structured-clone safe: plain objects, arrays, strings, finite numbers, booleans, `null`, `undefined`, `ArrayBuffer`, `Uint8Array`. Persisted data is JSON (`JsonValue`) and carries `schemaVersion` (or `version` for snapshots).

**Ids.**

| Thing                       | Format                                                                               | Example                         |
| --------------------------- | ------------------------------------------------------------------------------------ | ------------------------------- |
| Plugin id                   | dot-separated `[a-z0-9-]` segments; `forsee.*` first-party                           | `community.example-phrases`     |
| Command                     | `<area>.<verb>` built-in; plugin commands start with `<pluginId>.` or `<pluginId>/`  | `composition.insert`            |
| Contribution                | unique per extension point; plugins prefix `<pluginId>/`                             | `community.example/compact`     |
| Panel                       | `<ownerId>/<panelId>`                                                                | `forsee.phrases/picker`         |
| Gaze target                 | `<owner>/<local id>`                                                                 | `keyboard/key-a`                |
| Settings namespace          | `app.<area>` for the app, plugin id for plugins                                      | `app.gaze`, `community.example` |
| Context key                 | dot-separated topic path                                                             | `time.partOfDay`                |
| Voice provider              | app: bare id; plugin: `<pluginId>/<localId>`                                         | `community.voices/neural`       |
| Voice (global id)           | `<providerId>/<voiceId>`, voice id escaped (`%`→`%25`, `/`→`%2F`), split at last `/` | `forsee.web-speech/Samantha`    |
| History record, utterance   | UUID v4 from `IdSource.uuid()`                                                       |                                 |
| HLC timestamp (`HlcString`) | `<wall ms 15 digits>-<counter 6 digits>-<deviceId>`, sorts causally                  | `001763035200000-000000-dev1`   |

**Errors.** Kernel APIs throw or reject with `ForseeError` (`packages/core/src/errors.ts`), whose `code` is a `ForseeErrorCode` (`plugin-api/src/common.ts`); `toData()` gives the RPC form. Errors that must not reach the caller (a throwing event listener, a failed background save) go to an injected `ErrorReporter`. The default reporter raises an unhandled promise rejection, which shows in the console and fails a Vitest run.

**Events.** `EventBus<M>` (`core/src/event-bus.ts`) is synchronous and typed. One throwing listener never stops the others. Every kernel subsystem has its own `events` bus, and `createKernel` forwards them all onto `kernel.bus` (`KernelEventMap` in `core/src/kernel.ts`).

**Commands.** `kernel.commands.execute(id, args)` always returns a promise, but the handler runs synchronously inside the call, so a synchronous handler's effect is visible as soon as `execute` returns. Unknown ids reject with `unknown-command`; handler failures reject with `handler-error` (original error in `cause`). Built-in argument types are in `CommandArgsMap` (`plugin-api/src/commands.ts`); packages add their own by declaration merging (see `packages/layouts/src/contracts.ts`).

## The kernel (`packages/core`)

`createKernel(options)` (`core/src/kernel.ts`) wires:

| Member           | Type                           | File               | What it is                                                            |
| ---------------- | ------------------------------ | ------------------ | --------------------------------------------------------------------- |
| `bus`            | `EventBus<KernelEventMap>`     | `event-bus.ts`     | every kernel event                                                    |
| `commands`       | `CommandRegistry`              | `commands.ts`      | register/execute/list, before/after/failed events                     |
| `composition`    | `CompositionBuffer`            | `composition.ts`   | text being written, undo, snapshots, partial word and its uncertainty |
| `conversation`   | `ConversationLog`              | `conversation.ts`  | utterances with UUID, device id and HLC; tombstone deletion           |
| `settings`       | `SettingsRegistry`             | `settings.ts`      | schemas per namespace, validated get/set, load/export                 |
| `extensions`     | `ExtensionRegistry`            | `extensions.ts`    | contributions per extension point, by owner                           |
| `regions`        | `RegionModel`                  | `regions.ts`       | panels per screen region, visibility, size                            |
| `context`        | `ContextStore`                 | `context-store.ts` | shared context entries with source and expiry                         |
| `speech`, `gaze` | `SpeechService`, `GazeControl` | `services.ts`      | injected, optional                                                    |

Persistence is injected (`SettingsPersistence`, `ConversationPersistence`, `CompositionPersistence` in `core/src/services.ts`); B6 implements all three. `kernel.start()` loads settings, recent history and the composition snapshot, reporting (not throwing) persistence failures so the user can always type. Every composition change is saved in the background, with bursts coalesced.

Built-in commands: `composition.insert {text, distribution?}`, `composition.deleteGrapheme`, `composition.deleteWord`, `composition.clear`, `composition.undo`, `composition.acceptPrediction {text}`, `composition.speak {log?}`, `speech.speak {text, log?, voiceId?, rate?, pitch?, volume?, recording?, interrupt?}`, `speech.stop`, `gaze.pause`, `gaze.resume`. `composition.speak` (the Speak key) commits the composition, runs `commit` text transforms, appends to history and calls `SpeechService.speak`; `speech.speak` does the same for the text it is given and never touches the composition. When nothing can speak, both emit `speech.unavailable`. `composition.insert` of text ending in whitespace or punctuation runs `word-boundary` text transforms and applies the result only if the user has not typed since.

A minimal shell:

```ts
const host = createWebHost();
const kernel = createKernel({
  clock: host.clock,
  ids: host.ids,
  deviceId,
  speech,
  gaze,
  persistence,
});
await kernel.start();
await kernel.commands.execute('composition.insert', { text: 'h' });
```

## The application runtime (`apps/web/src/runtime`)

`createForseeRuntime(options)` boots everything behind the screen and returns one `ForseeRuntime` (types in `apps/web/src/runtime/types.ts`): `hostUi` (the `HostUiServices` the UI root receives), `kernel`, `host`, `profile` (storage backend, `persistent`, `warning`), `speech` (engine, `available`, `locked`/`unlock()`, settings), `gaze` (pipeline, targets, input mode, dwell faster/slower, pause/resume through the kernel commands), `prediction`, `layout` (catalogue, active definition and runtime, change event, `select`, `setFamily`), `settings`, `pluginHost`, `errors` (every reported error), `startupIssues`, `flush()` and `dispose()`. Boot order: storage and profile (OPFS, IndexedDB, then memory with a warning), kernel with crash recovery, speech, prediction, plugin host with the first-party plugins, gaze, layout, lifecycle (`pagehide` and hiding flush). An optional part that fails is reported and skipped. Every browser dependency is an option with a real-browser default, so the runtime runs in Node tests (`apps/web/src/runtime/testing.ts`). The React entry (`apps/web/src/main.tsx`, `App.tsx`, `MainScreen.tsx`) boots it once per page load, outside React, and mounts the `ui` components on it; see "Decisions: the assembled app".

## Decisions

Where the plan was silent or ambiguous, A2 chose as follows.

1. **Platform services live in `core`, not `host`.** `Clock`, `IdSource`, `ProfileFileSystem` and `FileSystemError` are in `packages/core/src/platform.ts`, so engine packages never depend on `host` (which may use the DOM). `HostBridge` composes them.
2. **Two clocks.** Monotonic for anything in-session, wall for anything persisted or crossing realms. The context store uses wall time for `expiresAt` because writers run in sandboxed realms with different `performance.timeOrigin`.
3. **Context permissions.** The plan says prediction providers "with permission" can read the context store but names no scope. A2 adds `context.read` and `context.write`.
4. **Settings namespaces.** One schema per namespace. App areas each register `app.<area>` (`app.general` is registered by the kernel and holds `locale`); plugins use their id. `label` is required (the gaze UI reads it out), and a bare string in `options` is shorthand for `{ label, value }` (the plan's manifest example uses that form). Values for namespaces whose schema has not loaded yet are kept and validated when it arrives; only explicitly set values are persisted.
5. **Two-speed prediction.** `predict(request)` returns `PredictionResult | Promise<PredictionResult>` (synchronous for in-process providers, a promise over RPC). `refine(request, cancellation)` resolves one refined result or `null`, rather than an async iterator, because a single resolution crosses `postMessage` cleanly. Every result carries the request's `requestId`; stale results are dropped. A candidate's identity is its `text`, and `CandidateStabiliser` keeps the dwelt-on candidate in its slot.
6. **Selection uncertainty reaches the predictor through the composition.** `composition.insert` takes an optional `distribution`; the buffer keeps `partialWordSteps` (one step per insert, concatenating to the partial word) and the prediction engine copies them into the request.
7. **Delete word** removes trailing whitespace and then the last whitespace-delimited token, punctuation included (`"Hello, world!  "` → `"Hello, "`). This is predictable, and one dwell removes what looks like one word.
8. **Accepting a prediction** replaces the partial word, matches a leading capital typed by the user, and adds an automatic trailing space. With no partial word it appends the word, inserting a separating space unless the text ends in whitespace or an opening bracket or quote. While the space is automatic, typing `. , ! ? ; :` moves the space after the punctuation, and typing a space is absorbed, so the user never gets `"word ."` or a double space.
9. **Commit** (`composition.speak`; until review round 1, `speech.speak` with no text) returns the trimmed text and clears the buffer as an undoable step, so "oops" is one dwell away. History logging happens even without a speech service.
10. **Grapheme deletion** uses `Intl.Segmenter` when the runtime has it, looked up structurally rather than through lib typings, with a tested fallback covering combining marks, variation selectors, skin-tone modifiers, tag sequences, ZWJ sequences, regional-indicator pairs and CRLF.
11. **Undo** is bounded (default 100 steps) and covers every text change, including commit and replace. There is no redo. Snapshots hold only the text in v1 (`version: 1`); restoring clears undo history.
12. **Key escalation and repeat** come from the gaze engine: a target with `afterActivate: 'repeat'` fires again while gaze stays, with `ActivateEvent.repeatIndex` 0, 1, 2…. A layout key with `behaviour: { type: 'escalate', steps }` maps `repeatIndex` to a step (delete letter, then word, then clear).
13. **Two-step group keys** are `LayoutGroupKey` (`group: true`, `keys`). Action keys, group keys and spacers are told apart by which of `action`, `group` or `spacer` is present, so layout JSON needs no `"type"` field on every key. Page switching is a command (`layout.showPage`), declared by `layouts` through `CommandArgsMap` merging.
14. **Pause and wake go through commands.** The kernel emits `gaze.pauseChanged` from the `gaze.pause` and `gaze.resume` commands. The gaze engine's wake target should therefore carry the command `gaze.resume`, so state never changes behind the kernel's back.
15. **Contribution ids** are unique per extension point across all owners, and a clash throws. The plugin host prefixes plugin contributions with the plugin id. `ExtensionRegistry.disposeOwner(pluginId)` unloads a plugin's contributions in one call.
16. **History deletion** is a separate `TombstoneRecord` kind (`targetId`), not a flag on the utterance, so history files stay strictly append-only.
17. **Persistent file systems.** The web host's profile is in memory for now (`capabilities.fileSystem: 'memory'`). B6 owns a persistent browser `ProfileFileSystem` (OPFS or IndexedDB), passed to `createWebHost({ files })`. A Node file system cannot live in an engine package (Node is banned there), so it belongs in the desktop shell (B11) or a new DOM-free, Node-allowed package. B6 and B11 should agree which.
18. **Region sizes are discrete** (`compact`, `normal`, `expanded`) so that resizing can be done by gaze with "bigger" and "smaller" keys.
19. **Panels render as a sandboxed frame or a first-party React component** (`PanelContribution.render`), registered with `PanelComponentRegistry` under the panel id.
20. **Browser APIs in engine packages are injected structurally.** The speech package is DOM-free, so the web speech provider takes a `SpeechSynthesisLike` and a `createUtterance` function, and the recorded-message provider takes an `AudioPlayer`.
21. **RPC** (`plugin-api/src/rpc.ts`) is symmetric request/response plus `event`, `cancel`, `release` and `hello`. Functions and handler objects travel as `RpcHandleRef`. Subscriptions use `event` messages, so hot paths need no round trip.
22. **`BuiltinCommandId` is an explicit union** rather than `keyof CommandArgsMap`, because other packages extend that map.
23. **UTF-8 helpers** (`encodeUtf8`, `decodeUtf8` in `core/src/utf8.ts`) exist because `TextEncoder` is not in the ES2022 library that engine packages compile against.
24. **Test doubles ship in the main entry of `@forsee/core`** (`FakeClock`, `SequentialIdSource`, `MemoryFileSystem`), so no subpath exports or extra tsconfig wiring is needed.
25. **Commands are private to their plugin by default.** A `CommandDescriptor` carries `public` and `requires`. A plugin can always run its own commands; it can run an app command or another plugin's command only if that command is public and the plugin holds every scope in `requires`. The built-in `composition.*` commands require `composition.write` and `speech.speak` requires `speech.output` (see review round 1 below for `composition.speak`, `speech.stop` and `gaze.*`). `CommandRegistry.authorize(id, caller)` implements the check; `execute` itself trusts its caller, so **the plugin host must call `authorize` before `execute` for every plugin-originated call** (B9, B10).
26. **Command failures keep their error code.** A `ForseeError` thrown or rejected by a handler reaches the caller unchanged (`invalid-argument`, `permission-denied`, ...). Only other failures are wrapped as `handler-error`.

### Decisions: permissions and speech (review round 1)

An external review found that the permission checks were made per method, while data reached plugins through other capabilities. These decisions fix that and the speech contract. Each is covered by tests in `packages/plugin-host/src/data-access.test.ts` and `packages/integration-tests`.

- **Permissions are about data and effects, not methods.** For every path into a plugin (API results and rejections, event payloads, command results, every argument the host passes to a provider or handler) the plugin must hold the scope of the data on it, checked at the moment of delivery, not only at registration. `packages/integration-tests/src/capabilities.test.ts` takes one capability away from a probe plugin that uses everything else and asserts the data never reaches it (composition without `composition.read`, history without `history.read`) or the effect never happens (any composition change without `composition.write`), each with an all-scopes control.
- **Prediction providers need `composition.read`.** Every request carries the composition. Registration needs it; the wrapper checks it on every `predict`, `refine`, `learn` and `forget` and does not call the plugin without it (`predict` answers an empty result); the registration is also disposed on revocation. App-owned providers registered directly in the extension registry are not wrapped and keep working as before.
- **Voice providers need `speech.output` and `composition.read`; text transforms need `composition.read` and `composition.write`.** Both are handed the composition (an utterance is what the user composed). Both are checked per call and disposed on revocation. The wrapper also validates the handle a voice provider returns.
- **`speech.speak` and `composition.speak` are separate commands.** `speech.speak {text, …}` requires non-empty `text`, requires `speech.output`, and never reads or changes the composition. `composition.speak {log?}` commits the composition (the Speak key) and requires `speech.output`, `composition.read` and `composition.write`; it returns the `SpeakCommandResult` the old no-text form returned. The built-in layouts' Speak keys use `composition.speak`. This is a deliberate breaking change to `CommandArgsMap['speech.speak']` (the no-text form leaked and cleared the composition).
- **Speak options reach the speech engine.** `speech.speak` takes the `SpeakOptions` (`voiceId`, `rate` 0.1–10, `pitch` 0–2, `volume` 0–1, `recording`, `interrupt`, `log`); the kernel validates them (unknown keys rejected; `recording` must be a safe profile-relative path: no leading `/`, no empty, `.` or `..` segment, no `\` or `:`) and passes all but `log` to `SpeechService.speak`. The plugin host accepts `interrupt`.
- **Nothing to speak with is reported, not silent.** `SpeechService` gains an optional `isAvailable()` (the speech engine: a synthesis provider is registered). With no service, `isAvailable() === false`, or a `speak` that rejects or resolves `error` (see "Decisions: application runtime"), the kernel emits `speech.unavailable {text, recordId, reason}`. The text is still logged (unless `log: false`) and, for `composition.speak`, one undo away.
- **One identity scheme for voices.** App providers have bare ids (no `/`); plugin providers are `<pluginId>/<localId>` (the plugin host prefixes, neither part has a `/`). A global voice id is `formatVoiceId(providerId, voiceId)` = `<providerId>/<voiceId with % → %25 and / → %2F>`, split by `parseVoiceId` at the last `/`. Both helpers live in `plugin-api/src/speech.ts`; the speech registry accepts provider ids with at most one `/`, and the web speech provider parses ids with `parseVoiceId`, so voice URIs containing `/` work.
- **Command results and undo are data too.** Results of the built-in `composition.*` commands (whether something was deleted or undone) reach a plugin only with `composition.read`. Undoing a commit brings spoken text back, so `composition.undo` at a commit step also needs `history.read` (`CompositionBuffer.nextUndoReason`).
- **`speech.event` is redacted without `composition.read`:** word boundaries (position and length of each spoken word) are dropped and error messages replaced.
- **Effects on the user's voice and input need a scope.** `speech.stop` requires `speech.output` (any plugin could otherwise silence the user); `gaze.pause` and `gaze.resume` are not public (a plugin could lock the user out of the keyboard, or resume selection while they rest).
- **The plugin API is provisional** until the first end-to-end release: `API_STABILITY = 'provisional'` in `plugin-api/src/manifest.ts`, explained in `packages/plugin-api/README.md`. It may change without an `API_VERSION` bump until then.
- **Not fixed here, for the components that own them:** the keyboard view must authorise the actions of keys in plugin-contributed layouts against the layout's owner (today they would run with keyboard trust); whoever translates panel targets must clip them to the panel frame (noted on `PanelTargets`); driver and in-process gaze sources are full input control and consent screens should say so.

### Decisions: activation and UI boundary (review round 1)

Taken after the first external review. Unnumbered, so the list above keeps its numbers.

- **Only observed dwell counts, and only a sample can fire.** The dwell method credits the interval between two consecutive valid samples to a target only when both samples hit that target (after hysteresis), the target could fire at both (enabled, not locked by look-away, the right role for the pause state), they are at most `holdMs` apart, and no invalid sample came between. Anything else (another target, a rest zone, empty space, an ineligible target, a blink, a longer gap) gives the previously engaged target nothing for the gap; it then holds and decays, or resets in a rest zone, as before, and a newly engaged target starts at its own first sample. A target fires only on such a confirming sample, never on a frame tick. Ticks show a provisional fill of at most `extrapolateMs` after the last valid sample, which is display only and is dropped if the next sample does not confirm the target.
  - _Guarantee:_ every activation happens at the time of a valid sample that hit the fired target, and every millisecond counted toward it lies between two consecutive valid samples that both hit it, at most `holdMs` (default 300) apart. No unconfirmed (extrapolated) time ever counts. What a source cannot observe between two such samples (a glance away and back inside one interval) is counted; nothing else is.
  - _Trade-off:_ a threshold that falls between samples fires on the next sample, so up to one sample interval late: about 17 ms at 60 Hz, 200 ms at 5 Hz. A slow source that stays on the target fires at the configured time when the threshold falls on a sample, and is never early. Sources slower than about 3.3 Hz (`1000 / holdMs`) cannot dwell at all, as before. Preferring a late selection to an unintended one is deliberate: unintended selections are the most damaging failure for this product.
- **Exactly one party executes an activation.** A target with a `command` is executed by the gaze pipeline, once, with the distribution attached; a target without one (layout keys, plugin panel targets) is executed by its owner, and the pipeline executes nothing. `GazePipeline.onActivate` listeners receive the full `ActivateEvent` and an `ActivationOutcome` (`executedBy: 'pipeline' | 'owner'`); owners act only on `owner` outcomes for their own target ids. A wake target without a command is resumed by the pipeline (`executedBy: 'pipeline'`).
- **Every owner attaches the distribution the same way:** `withActivationDistribution(invocation, event)` in `@forsee/gaze` returns the invocation with the activation's `KeyDistribution` added when the command is `composition.insert`, its args carry none, and the distribution is not empty; otherwise it returns the invocation unchanged. The pipeline uses it too.
- **Activation callbacks get the whole event.** `GazeTargetProps.onActivate` receives the `ActivateEvent` (target, method, `repeatIndex`, point, distribution, time) instead of only `repeatIndex`; when the target also has a `command`, the callback is for feedback and must not execute it again. The keyboard view's **activation adapter** (`ActivationAdapter` in `packages/ui/src/contracts.ts`, types only) maps an owner activation of a layout key to `LayoutRuntime.activate(keyId, repeatIndex)`, attaches the distribution with the helper and executes the action exactly once.
- **Panels receive the distribution for their own targets without `gaze.read`.** `PanelActivation` gains optional `point` and `distribution` (additive). Key probabilities reveal roughly where the user looked, but only around the panel's own target at the moment it fired, which describes the plugin's own UI; `gaze.read` still guards the gaze stream. The host must clamp `point` to the panel frame (panel-relative coordinates) and keep only the panel's own targets in `distribution` (panel-local ids, renormalised, fired target present), so an activation never says anything about other owners' targets or where the user looked outside the panel. The plugin host's `PanelTargetRegistry.activate` currently passes only `repeatIndex`; filling the new fields there is follow-up work in `packages/plugin-host`.
- **Trusted host infrastructure versus features.** Two kinds of UI code, so that there is one extension system:
  - _Trusted host infrastructure_ may use the kernel directly: the app frame and regions, the keyboard view and gaze targets, dwell feedback, the settings shell, calibration, and the plugin host itself. It receives `HostUiServices` (formerly `UiServices`: kernel, gaze pipeline, prediction engine).
  - _Features_ are first-party plugins built on the public `ForseeApi` through the plugin host: the prediction strip's data, phrases, quick-fire replies, history, partner display content, any provider. A feature panel's component receives its plugin's `ForseeApi` (`PanelComponentProps.api`, registered with the component in `PanelComponentRegistry.register(panelId, component, api)`) and never the kernel. Where `ForseeApi` lacks something a feature needs, the API is extended additively, never bypassed. Known gap: `ForseeApi` has no way yet to read the current prediction candidates, which the prediction strip needs.

### Decisions: application runtime

Taken while wiring the engines into one app (`apps/web/src/runtime`). Each fix was made at its source and is pinned by a cross-package test in `packages/integration-tests/src/runtime-seams.test.ts` or the package's own tests.

- **The plugin host supplies the prediction engine's `access` hook:** `createPredictionEngine({ access: predictionAccess(pluginHost.permissions) })`. The engine's default denies `learn` to every provider not owned by the app, so without it a predictor registered through the plugin API never learned, whatever its permissions. `predictionAccess` applies the wrapper's rules (`history.read`, `context.read`, `lm.write`, each also needing `composition.read`).
- **A speech end with reason `error` is a failure.** The speech engine resolves `error` and never rejects, so the kernel now emits `speech.unavailable` (`reason: 'error'`) when `SpeechService.speak` resolves `error`, as well as when it rejects.
- **`createWebHost({ files, persistent })`:** `capabilities.fileSystem` reports what `createBrowserFileSystem` found; its in-memory fallback is not persistent.
- **First-party plugins:** word prediction (`plugins/prediction-ngram`, `forsee.prediction-ngram`) and quick-fire replies (`plugins/quickfire`, `forsee.quickfire`) are plugins on `ForseeApi`. Their manifests have no `main` (the validator requires a `.js` bundle and they run in-process from source), so the host reports their tier as `declarative`.
- **Where the runtime keeps plugin state:** consent records in `state/plugin-consent.json`, install records in `state/plugins.json` (not under `plugins/`, where any name is a valid plugin id). The n-gram plugin keeps the learned user model in its private storage (`plugins/forsee.prediction-ngram/data.json`), because `ForseeApi` cannot reach `lm/user-counts.json` (see the gap below).
- **App settings namespaces:** `app.speech` (`voiceId`, `rate`, `pitch`, `volume`, `speakMode`), `app.layout` (`layoutId`, `family`), `app.gaze` (`GAZE_SETTING_FIELDS`). The selection method follows the input: touch selects directly, mouse, pen and trackers use `app.gaze/selectionMethod`. `gaze.dwellFaster` and `gaze.dwellSlower` are app commands (not public) that step dwell, store it and say the new value with `log: false`, which is neither history nor learned.
- **Known API gaps (not changed):** `ForseeApi` has no access to the profile's personal language data (`lm/user-counts.json`, scopes `lm.read`/`lm.write`), and a private storage value is capped at 1 MB, which a large user model can exceed; and `PluginHost.dispose` does not call `deactivate`, so plugins must not hold unsaved state (the n-gram plugin's `learn` resolves only once its save has finished).

### Decisions: the assembled app

Taken while assembling the first working version (`apps/web/src`). Status and known rough edges are in [MVP_STATUS.md](MVP_STATUS.md).

- **The shell stays thin.** `apps/web/src` holds only wiring: boot and failure screens, the main screen, the settings sheet's choice of sections, notices, and hooks onto the runtime. Reusable pieces were added to `packages/ui` with tests (`Sheet`, `ChoiceGroup`, `ToggleTarget`, `StepperControl`, `PhraseBar`, `NoticeCard`, `StopSpeakingButton`, `useMediaQuery`, `AppFrame`'s banner row and `inert`).
- **Speak exists once.** The layouts' own Speak key (`composition.speak`) is the way to speak; the side bar has Stop (only while speech plays, its place otherwise kept as a rest area so nothing moves), Faster/Slower with the letter dwell shown (the runtime's `gaze.dwellFaster` / `gaze.dwellSlower` commands, which store and announce the value), Pause and Settings. A layout without a Speak key gets the side-bar Speak button instead.
- **Quick-fire replies are feature data.** The row reads the phrase set the `forsee.quickfire` plugin contributed (`kernel.extensions.list('phraseSets')`, owner `forsee.quickfire`) and binds each tile to the plugin's public command `forsee.quickfire.speak`; the app knows those two ids, not the phrases. Without the plugin the row is absent. It sits in a banner row above the text (the keyboard keeps at least 55 % of the height; about 60 % at 1024 x 768) and gives way to the "turn on speech" prompt while the browser holds speech.
- **`app.ui` settings** (runtime): `clickSound` and `physicalKeyboard`, both on by default. Physical keys go through the kernel commands (`composition.insert`, `composition.deleteGrapheme`, `composition.speak`), never inside a dialog, never while paused.
- **`runtime.reportError`** lets the UI put its own failures (a click whose command failed) in the same error stream as the runtime's; the Settings button shows their count and the sheet lists them.
- **Notices sit beside the text, never over keys.** Storage that does not persist, and text that could not be spoken (`speech.unavailable`): the text is shown for the partner to read and can be put back into the message (undo of the commit, or typed again).

## Things that will trip you up

- **`exactOptionalPropertyTypes` is on.** You cannot assign `undefined` to an optional property; spread conditionally: `...(x === undefined ? {} : { x })`. **`noUncheckedIndexedAccess` is on**, so `array[i]` is `T | undefined`.
- **Engine packages compile against bare ES2022.** There is no `TextEncoder`, `structuredClone`, `console`, `setTimeout`, `AbortSignal`, `queueMicrotask`, `Buffer` or `process`, and that includes your test files, because `tsc -b` typechecks `src/**/*.test.ts` too. Use the `core` helpers (`Clock`, `CancellationSource`, `encodeUtf8`). In a test, `declare function structuredClone<T>(v: T): T;` is acceptable.
- **Vitest does not typecheck.** `pnpm typecheck` does. Type-level contract tests (`expectTypeOf`) only fail there.
- **`commands.execute` returns a promise even for synchronous handlers.** Await it, or `void` it if you deliberately fire and forget, because lint rejects floating promises.
- **`kernel.start()` must be awaited** before relying on restored settings, history or composition, and it can be called only once.
- **Monotonic timestamps are not portable.** Do not persist `t` values or compare them across a sandbox boundary.
- **`CompositionState.partialWord` is empty after punctuation**, so `"Hello,"` has no partial word, and accepting a prediction then appends `" word "`.
- **Settings throw on unknown keys.** Register your schema before `get`/`set`, under your own namespace (`app.<area>` or your plugin id).
- **`ExtensionRegistry` never calls contributions**; consumers watch `extensions.events` (`changed`) and re-read `list(point)`.
- **Avoid changing `plugin-api` if you can.** Every package compiles against it. If you must, change it additively (new optional fields, new types), never rename, and note it in your pull request.
- **Never import `@forsee/host` from an engine package**, and never import `node:*`, `react` or `electron` there; lint enforces this.
