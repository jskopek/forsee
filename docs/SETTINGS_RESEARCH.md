# Settings research: what Forsee should let people tune

Research and design note for making Forsee deeply customisable (VS Code style: a plain JSON file, a searchable settings screen, hundreds of entries), so that users and their therapists can tune what today are guesses, and so that tuned settings can, with explicit consent, flow back to improve the defaults. No code was changed for this note.

## Summary

**What other products expose (rough counts).** OptiKey stores 218 user settings (read from its source); Dasher about 110 parameters; HeliBoard about 170 preferences; AsTeRICS Grid about 90 fields across its input, colour, text and voice models; eViacam about 40; Cboard about 25; Project Gameface 8 to 13 cursor values plus one threshold per face gesture. From documentation extracts: Tobii Dynavox gaze interaction 20 to 30 (dwell per button and keyboard, feedback type, colour and size, look-away, switch timing, zoom); Grid 3 access settings a few dozen; Apple Dwell Control about 8 on macOS and about 10 on visionOS; Android Camera Switches and Switch Access about 15; Windows Eye Control about 6; Look to Speak about 6. Products aimed at specialists (OptiKey, Dasher, Grid 3, Tobii Dynavox) expose the most gaze timing. Operating-system features expose the fewest.

**What Forsee has.** 26 registered settings in 6 namespaces (`app.general` 1, `app.gaze` 15, `app.speech` 5, `app.layout` 2, `app.ui` 2, `app.plugins` 1). The settings sheet shows 6 of them directly (layout, voice, rate, when to speak, click sound, physical keyboard) and can reset the four dwell times. About 70 more hard-coded values change behaviour or feel (part 2).

**The catalogue (part 3)** has **315 candidate settings**: **43 now** (the code already supports them: 26 registered and 17 that only need a schema entry), **167 soon** (a small change in an existing package) and **105 later** (they depend on webcam gaze, calibration, the phrase bank, the partner display, the desktop app, swipe typing or the alarm). It also gives a "first hour" set of 28, 12 groups of interacting settings with 7 presets, and 24 dangerous settings with the guard each one needs.

**The five most important recommendations**

1. **Add metadata to `SettingField`, then generate the settings screen from the schema** (category, order, unit, audience, danger level, requires-restart, scope, display hints, and `list`/`map` types). The registry already validates, persists only non-default values and keeps unknown keys. What is missing is the metadata a searchable, gaze-operable UI needs (part 4.2).
2. **Guard dangerous changes before exposing more of them.** Use a timed "Keep these settings?" check that must be confirmed with the new settings, a caregiver gate for lockout-level settings, hard floors and ceilings that a file import cannot bypass, and a safe-mode start. Today `selectionMethod` can be set to `switch` although no switch source exists, which locks out an eye-only user (part 3.4).
3. **Add layers to the registry:** defaults, then preset, profile, input-device override, layout override and context ("tired"). This lets a webcam session, a tracker session and an evening session each keep their own dwell without the user retuning every time. Every value shows where it came from (part 4.3).
4. **Ship presets as data**, and make one-step changes the main way to tune ("new user", "experienced", "webcam", "low vision", "tremor or nystagmus", "tired"). Individual settings stay available below them. Many settings only make sense in groups (dwell, decay, hold, hysteresis, smoothing; part 3.3).
5. **Measure locally, suggest, never change silently; then share only by explicit export.** Keep counters on the device (selections, quick undos, abandoned dwells) to drive suggestions such as "try 100 ms slower". Share tuned settings as a reviewed diff from the defaults with coarse context. Never include text, history, vocabulary, device id or gaze recordings. The default way to share is to export a file (part 4.6).

### 1.2 Tobii Dynavox [extract]

- **Windows Control and Gaze Interaction Settings:** Activation is Dwell or Switch. **Button Dwell Time** and **Keyboard Dwell Time** are set separately (Button Dwell has 8 levels on the I-Series). **Look Away Before Reselecting** stops the same item firing twice. Switch mode adds **Minimum Click Duration** and **Duration Between Clicks** (dead time). **Feedback Type** is rotating clock, shrinking dot or none, with **Feedback Color** and **Feedback Size**. Gaze Selection (two-step) mode has zoom **Precision** and **Speed**. There is a choice between Gaze Selection and Mouse Emulation.
- **Communicator 5:** activation Dwell (default), Switch or Blink. **Keyboard Dwell Time defaults to 1200 ms, range 100 to 4000 ms in 50 ms steps**. Gaze settings appear only when a tracker is connected. Profiles store dwell time.
- **TD Snap:** a per-button dwell time that overrides the user setting (version 1.18 and later).
- **TD Pilot (iPad, Apple AssistiveTouch):** setup sheets suggest starting at **1.5 s dwell with movement tolerance of 25% or more**. Pointer colour and size can be changed.

### 1.3 Smartbox Grid 3 [extract]

Settings, Access, Eye gaze: activation **blink, dwell or switch to click**, an optional **eye gaze dot**, **dwell time +/-**, a separate **computer control dwell**, **zoom to click time** and magnification, **Fast typing** (halves the dwell on letter cells), **Rest** (eye gaze disabled for every cell but one), calibrate and improve calibration, and an eye gaze viewer with camera feed. Pointer and touch settings include a choice of **dwell timer appearance**. **Prevent repeat activations within a set period** allows a repeat on the same cell but makes others wait. Most settings can also be changed by grid commands placed on cells, so a user can have a "dwell slower" cell.

### 1.7 Research and clinical guidance [extract]

- **Dwell time is personal and changes with practice.** Novices in early studies used 450 to 1000 ms (5 to 10 words per minute). With **adjustable dwell**, inexperienced users reached about 20 wpm after 10 sessions of 15 minutes, with no loss of accuracy (Majaranta, Ahola and Špakov, CHI 2009). At 1000 ms speed tops out near 12 wpm. 700 ms or less suffices for simple tasks (Majaranta et al., UAIS 2006). One ergonomic study found 600 ms easiest, and another found 500 ms best overall. Microsoft Research's cascading dwell work adjusts dwell per key from language likelihood (title only found).
- **Automatic dwell adjustment has drawbacks.** Users found system-driven speed changes hard to control (arXiv 1601.06359, extract). This supports Forsee's approach: suggest changes, apply only when the user confirms.
- **Target size should follow tracker quality:** size targets so that about 95% of gaze samples land inside, from measured accuracy and precision (Feit et al. 2017, Microsoft Research). Small controls are hard to lock onto.
- **Fatigue, vision and positioning (Eyegaze Edge clinical notes, vendor experience):** short dwell reduces fatigue, but eyelid muscles tire. Put the screen slightly low for **ptosis** (drooping lids), since some systems need the full pupil. **Nystagmus** under about 3 beats per second can work, and longer fixation windows help. Some trackers cannot calibrate an eye whose signal is unstable. For such users, tracking one eye (visionOS offers left or right only) is the usual workaround [one-eye clinical guidance unverified].
- **Not found:** peer-reviewed clinical protocols for individualising eye-gaze settings for AAC users. Most guidance is vendor training material (Tobii Dynavox pathways, Smartbox lessons). Forsee's local statistics and opt-in sharing (part 4) would help fill this gap.

### 2.3 Observations from the audit

- **Registered settings without effect:** `filter.minCutoff` and `filter.beta` only act on `gaze` sources, and the only source today is the pointer, which is never filtered.
- **Lockout through a registered setting:** `selectionMethod: switch` or `direct` with an eye tracker that moves the pointer means nothing can be selected by gaze. No switch input is wired in `apps/web`, so in `switch` mode only a mouse click or tap confirms. The setting has no screen today. It is reachable only through an imported `settings.json` or a future generated screen.
- **Inconsistent bounds:** the schema allows dwell from 100 ms, the Faster key stops at 200 ms, and the screen offers rate 0.5 to 2 while the schema allows 0.1 to 10. Bounds should come from one place, the schema, with separate "safe" and "allowed" ranges (part 4.2).
- **Multi-key updates are not atomic:** `adjust` sets up to 8 keys one by one. Each change emits an event, saves and reconfigures the pipeline. A preset would do the same 30 times. The registry needs a batch set (part 4).
- **Values are primitives only** (`string | number | boolean`), so per-key dwell, quick reply lists, blocked words and pronunciations cannot be settings yet.
- **The settings screen is hand-written** (5 sections, 6 settings and a dwell reset). The plan calls for a screen generated from schemas.

## Part 3: The settings catalogue

### 3.1 Conventions

- **Key:** `<area>.<group>.<name>`, lower camel case, unit suffix where there is a unit (`Ms`, `Px`, `Hz`, `Percent`, `Days`). The first segment is the namespace without the `app.` prefix: `gaze.dwell.letterMs` is namespace `app.gaze`, key `dwell.letterMs`. Existing keys keep their current names. Booleans are named positively (`enabled`, `requireLookAway`), never `disableX`.
- **For:** E everyone, A advanced (hidden until "show advanced"), T therapist or caregiver (advanced and gated when dangerous).
- **Stage:** **now** = the code supports it and it needs only a schema entry (**now (reg)** = already registered); **soon** = a small change in an existing package; **later** = needs a feature that is not built yet.
- **From** abbreviations: OK OptiKey, TD Tobii Dynavox, G3 Grid 3, WEC Windows Eye Control, AP Apple, AN Android, DA Dasher, AG AsTeRICS Grid, CB Cboard, GF Project Gameface, EV eViacam, CM Camera Mouse, LTS Look to Speak, P4T Proloquo4Text, PR Predictable, SA Speech Assistant AAC, HB HeliBoard, FU FUTO, R research, F a Forsee constant (part 2).

### 3.4 Settings that interact, and presets

| Group                 | Settings                                                                                                                          | How they interact                                                                                                                                                                                                                                                                                             | Offer as                                                                             |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |

| Adaptive dwell        | `dwell.adaptive*`, class times                                                                                                    | Effective dwell is the class time times a factor between min and max. ### 3.5 Dangerous settings and their guards

A bad value here could lock an eye-gaze user out, make the keyboard unusable or fire selections the user did not intend. Guards: **B** hard bounds that file import and plugins cannot bypass; **R** timed "Keep these settings?" revert, confirmed by dwelling with the new settings; **C** caregiver gate (PIN or touch-only); **S** safe-mode start restores input defaults; **D** detect before offering.

The **timed revert** must be confirmed with the new settings: after a risky change the screen shows "Keep these settings? Undoing in 15 s" with a large Keep target. Dwelling on it proves the new values work. Any other outcome (timeout, Undo, a crash) restores the previous values. The **safe-mode start** (a URL flag, a held key on start, or automatic after two failed starts in a row) loads input, dwell and layout defaults for that session only. It shows a banner with "keep safe values" and "go back to mine".

## Part 4: How to manage hundreds of settings

### 4.1 File format, naming, versioning

**What exists:** `settings.json` in the profile folder is `{ "version": 1, "values": { "<namespace>": { "<key>": value } } }` (`packages/storage/src/profile.ts`). Only explicitly set values are stored (`SettingsRegistry.export`). Values for namespaces whose schema is not loaded are kept and validated later. The profile is exported and imported as an archive (`packages/storage/src/archive.ts`).

**Recommendations**

- **Keep one human-editable JSON file with only non-default values.** This is VS Code's model and what the registry already does. Nest by namespace as today. A flat dotted map would read more like VS Code, but nesting keeps plugin values apart and matches `SettingsSnapshot`.
- **Comments:** the app rewrites the file on every change, so comments would be lost. Accept JSON with comments on import, but write plain JSON. On desktop, a later "Open settings file" editor can preserve comments, as VS Code's does.
- **Schema file for editors:** generate `settings.schema.json` (JSON Schema) from the registered schemas, as `layout.schema.json` already exists for layouts. Ship it in the repository and the app. Add a `$schema` field to `settings.json` so editors autocomplete keys and check ranges.
- **Naming:** the rules in part 3.1. One `area.group.name` key per value, a unit suffix, positive booleans.
- **Versioning and migration:** keep the file `version`. Add a registry-level rename table, `renamed: { "app.gaze/dwell.letterMs": "app.gaze/dwell.letter.ms" }`, applied on load before validation, so a renamed key keeps its value. Add per-field `migrate(value, fromVersion)` for unit changes, for example pixels to degrees. Keep unknown keys as now, so a newer file survives an older app.
- **On invalid stored values:** add a per-field choice, `onInvalid: 'default' | 'clamp'`. Today invalid values are dropped and fall back to the default. That is safe for dwell, but clamping is safer for volume floors and kinder for sizes.

### 4.2 Schema extension

Today `SettingField` has `key`, `label`, `type`, `description`, `default`, `options`, `min`, `max` and `step` (`packages/plugin-api/src/settings.ts`). Proposed additions, all optional:

| Field                      | Purpose                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `category`, `order`        | Place in the settings tree (area, then group) and order within it                                                  |
| `unit`, `displayScale`     | `ms`, `px`, `Hz`, `%`, `x`; `displayScale` shows 800 ms as "0.8 s"                                                 |
| `safeMin`, `safeMax`       | The range offered by gaze; `min`/`max` stay the hard validation bounds                                             |
| `tags`                     | Search terms ("speed", "jitter", "tired")                                                                          |
| `audience`                 | `everyone`, `advanced`, `therapist`                                                                                |
| `danger`                   | `none`, `caution` (timed revert), `lockout` (revert and caregiver gate)                                            |
| `requiresRestart`          | Shown next to the control, as OptiKey does                                                                         |
| `scopes`                   | Layers that may set it (`profile`, `device`, `layout`, `context`); for example `layout.layoutId` is not per layout |
| `stage`, `since`           | Hidden until supported; the version it appeared in                                                                 |
| `deprecated`, `replacedBy` | For renames                                                                                                        |
| `enabledWhen`              | Shown only when another value matches (`selectionMethod == 'dwell'`)                                               |
| `related`, `preset`        | Settings to show beside it; the preset group it belongs to                                                         |
| `control`                  | `stepper`, `choice`, `toggle`, `colour`, `voice`, `list`, so the generated gaze UI uses the right control          |
| `preview`                  | Whether a live try-it area applies                                                                                 |
| `secret`, `shareable`      | Never exported or shared, for example plugin API keys; allowed in a shared settings report                         |
| `onInvalid`                | `default` or `clamp`                                                                                               |
| `type: 'list' \| 'map'`    | With an item schema: per-key dwell, quick replies, blocked words, pronunciations, colours                          |

The registry's `validateSettingFields` and the plugin host's `validateSettingFieldsJson` (with its `SETTING_FIELD_KEYS` list) must learn the new fields together. Cross-field rules, for example lock-on shorter than dwell or the safe dwell floor, need a per-namespace `validate(values)` hook. That hook does not exist today.

Long content does not belong in settings, even with `list`: phrase banks, pronunciations of hundreds of names and vocabularies are documents in the profile (`phrases/`, `lm/`). Settings should only point at them.

### 4.3 Layers and scope

**Today** the registry has one layer: `get` returns the stored value or the default.

**Proposed order**, lowest priority first: built-in default (schema), **preset** (a preset applied as a layer, so "modified from preset" and "back to preset" work), **profile** (the user's own values), **input-device override** (keyed by source kind and id, for example `when: { source: 'webcam' }`), **layout override** (`when: { layout: 'forsee/en-coarse-groups' }`), **context** (named and switched by the user, a schedule or a suggestion: "tired", "in bed", "outdoors"), **session** (temporary, cleared on restart: try-it trials and safe mode).

- The more specific layer wins, in the order above. A field's `scopes` limits which layers may set it.
- `set` writes to the most specific active layer that already sets the key, otherwise to the profile. The UI shows provenance ("from Webcam override") and lets the user move a value up or down a layer.
- **Persisted form** (version 2), like VS Code's language-specific blocks: `{ "version": 2, "preset": "new-user", "values": {...}, "overrides": [ { "when": { "source": "webcam" }, "values": {...} } ], "contexts": { "tired": {...} }, "activeContexts": [] }`. A migration moves version 1 `values` unchanged.
- **Gaps:** layered storage and resolution; a change event that fires when a layer becomes active (all affected keys change at once); a batch `setMany` or transaction so a preset or an adjustment emits one change and one save, not 30.

### 4.4 Presets, import, export and sharing a file

- **Presets are data:** JSON files with an id, name, description, audience and a partial values snapshot, shipped with the app. Plugins should be able to contribute presets as a new declarative contribution kind, next to themes and layouts. That kind does not exist yet.
- Applying a preset replaces the preset layer. The user's own changes on top stay visible as "modified".
- **Settings-only export:** a small file `forsee-settings.json` with the profile layer, overrides and contexts. Leave out `secret` fields and per-device values (tracker id, camera, audio device). The full profile archive already exists for complete backups.
- **Import:** show the differences first ("12 settings will change"), group them by danger, and apply the whole import under one timed revert.

### 4.5 A settings screen that works by gaze with hundreds of entries

What exists to build on: `Sheet`, `ChoiceGroup` with paging (the voice list), `StepperControl`, `ToggleTarget`, `useSetting`, `registry.reset(namespace, key)`.

- **Generated from the schema**, grouped by `category`, ordered by `order`, with `audience` filtering. Advanced and therapist entries are hidden until `care.showAdvanced` is on.
- **Entry points:** "First hour" (part 3.3) first, then Presets, Categories, "Changed from default" (the registry's exported values), "Recently changed" (a change log of the last 50 changes with time and previous value, which also gives undo for settings) and Search.
- **Search by gaze:** reuse the main keyboard and prediction to type the query, matching `label`, `description` and `tags`. Results appear as large paged targets. A short query usually suffices, since tags hold synonyms.
- **Controls:** a stepper for numbers (step and display scale from the schema), a choice grid for selects (paged), toggles, a colour grid, a voice list. Each row offers "reset to default" (and "reset to preset" when that differs). Values outside `safeMin`/`safeMax` can be set only from the caregiver (touch or mouse) layout.
- **Live preview:** a try-it strip in the dwell, feedback and target categories: five sample keys and a word prediction driven by the real pipeline, with changes applied to the session layer until confirmed.
- **Main-screen quick controls:** Faster and Slower already exist. Make the side-bar slots configurable (`ui.quickControls`: up to three of dwell, speech rate, volume, speak mode, theme, context). The settings shown on the main screen are the ones people change several times a day.
- **Caregiver layout** (`care.settingsInput: touch`): dense lists, sliders and a real text search, for a therapist with a mouse or touch screen.

### 4.6 Adaptive suggestions from local statistics

- **Collect** only counters, in `state/usage-stats.json`, kept for `adapt.stats.retentionDays`. Store aggregates per day: selections per class; selections undone or deleted within 2 s (a likely unintended selection); abandoned dwells (progress over 50% that decayed); time from first look to selection; wake attempts; sample rate and tracking-loss time; Faster and Slower uses. Never store text, key sequences or gaze positions.
- **Rules** (start simple, publish them, make them testable). Some examples. If likely-unintended selections are above 8% over the last 300 letter selections, suggest +100 ms on letters. If abandoned dwells are frequent and corrections rare, suggest a longer forget time (lower decay). If the user presses Faster three days in a row, suggest the experienced preset. If tracking loss is high, suggest recalibration or the webcam preset.
- **Presentation:** at most one suggestion at a time, only at a rest moment (`adapt.suggestions.when`). Each one gives the reason in a sentence, offers "try for 5 minutes" (session layer, then keep or undo), and can be dismissed for good. Never apply a change silently. This follows the research finding that system-driven dwell changes were hard for users to control.

### 4.7 Opt-in sharing of tuned settings with the project

Forsee's promise is offline use, so nothing is sent automatically, ever.

- **What a report contains:** the diff from defaults (profile, overrides and contexts) for fields marked `shareable`; the preset used; app version; platform (operating system family, browser engine); input kind and tracker model from a fixed list; screen size and sample rate rounded into buckets; layout id; language without region; weeks of use as a bucket; the local statistics aggregated over the whole period (unintended-selection rate, speed bucket). It also contains optional, self-described context chosen from lists: condition category (for example "motor neurone disease"), years of gaze use, eye or vision factors (nystagmus, ptosis, glasses, one eye), and who tuned the settings (user, family, therapist).
- **What it must never contain:** typed or spoken text, history, phrases, vocabulary or the user language model, plugin data, recordings, gaze samples (unless a separate, research-specific consent exists), names, the profile or device id (`profile.metadata.deviceId` must be stripped), exact dates, IP-derived location, and `secret` fields.
- **Review before sending:** the user (and caregiver) see the exact JSON and a plain-language list ("Letter dwell: 650 ms (default 800)"), can remove any line, and must confirm by dwell on a clearly labelled target. Health context is optional and marked as sensitive. It should be left out by default.
- **How it leaves the device:** (1) **export a file** (the default; it can be emailed by a caregiver or attached to a GitHub issue through a template), or (2) an explicit one-time send to a published project endpoint, available only when online, after the review screen. Each report gets a random report id, shown to the user, so they can ask for deletion. There is no account and no persistent identifier.
- **What the project needs:** a published report schema and its version; an intake (a GitHub issue form with the file attached, or a small endpoint that writes to a private store); validation and stripping on intake; a privacy notice and a retention policy (condition data is special-category health data under GDPR, so explicit consent and minimal fields are needed); an aggregation script that publishes per-input-kind distributions for each setting (median, quartiles, n); and a process that turns those into new defaults and presets. Changes to defaults should be documented in the changelog with the evidence.

### 4.8 Plugin settings

- **What exists:** plugins declare `contributes.settings` (validated JSON) or call `api.settings.registerSchema`, which replaces the earlier schema. Their namespace is the plugin id. Values persist even when the plugin is not loaded (restricted mode). The registry rejects keys and values that do not fit the schema.
- **Recommendations:** show plugin settings under "Plugins › <name>" by default. Let a plugin set `category` to join a core area (a voice plugin under Speech) with a "from plugin X" badge. Require `label` and `description` (labels are already required) and run `audience`/`danger` through the same guards as core settings. Plugins must not mark their own settings `danger: none` when they control input; the host should apply `caution` to any plugin setting in an input category. Honour `secret` (never exported or shared). Include plugin settings in presets only when the plugin is installed. Uninstalling a plugin should offer to delete its stored values, which are kept today.
- **Gaps:** no category or metadata fields; no `secret` flag; no plugin-contributed presets; a plugin cannot declare that it reads a core setting (for example `speech.rate`). Reading core settings may need a permission scope if they ever include anything sensitive.

### 4.9 Gaps in the registry, in one list

1. Values are primitives only; no `list` or `map` types.
2. No metadata for the UI (category, order, unit, audience, danger, restart, scope, safe range, control, tags, secret).
3. One layer only: no presets, input-device, layout, context or session layers, and no provenance.
4. No batch set or transaction: multi-key changes emit and save once per key.
5. No key rename or per-field migration; the file version exists but is not used for migrations.
6. No cross-field validation hook.
7. No change log, so no "recently changed", no undo for settings and no timed revert.
8. No reset for a whole category or namespace (only per key).
9. `step` is checked only for `range`, not `number`.
10. Bounds are duplicated outside the schema (`DWELL_ADJUSTMENT_DEFAULTS`, the settings sheet's rate range), and gaze-safe and absolute ranges are not distinguished.
11. Most engine configuration (filter kind, fixation, hold, distribution) has no schema entry; the filter settings that are registered have no effect for pointer sources.
12. The settings screen is hand-written, not generated from schemas.
13. No guard against lockout values (`selectionMethod: switch` without a switch).
14. No secret flag for plugin settings, and no plugin presets.
